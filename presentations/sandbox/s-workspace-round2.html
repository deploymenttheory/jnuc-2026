Option A - the anatomy of a workspace, then the lenses live now

A diagram across the top, following HashiCorp's own workspace anatomy: Terraform code in on the left, an HCP Terraform box holding the workspace boundary and its compartments (state file, variables and secrets, permissions, workflow, notifications, and more), the plan, policy and apply run stages beside it, and an arrow out to one Jamf Pro instance. Underneath, the lenses that decide how an instance gets carved up - team structure, deployment frequency, scale and what changes together - with a closing line for the factors that refine the choice rather than drive it. Deliberately names no patterns. The cost run stage from the source diagram is left out: it estimates cloud spend and does nothing for a Jamf Pro instance. Pick this if the slide has to carry both halves of the message - what a workspace is, and that carving an instance up deserves unhurried thought. This is what ships in the deck from this PR; accepting it means deleting the ws-opt-b, ws-opt-c and ws-opt-d wrappers from the #s-workspace section.

Option D - the design logic behind the split

    
Four numbered moves, not a diagram or a table: one link and one state is what a workspace actually is; scale forces the first split (guidance's roughly-500 ceiling against this estate's 1,500+); then split by what changes together, which is why each instance runs three workspaces - iam, profiles_policies, root - rather than one; then stop splitting once it stops paying off, which is why DevTest gets one workspace and Sandbox gets none. Distilled from the Microsoft 365 provider's Terraform Cloud workspace-design guide - its workspace-to-repository/state model, its resource-scale and blast-radius thresholds, its service-domain splitting pattern, and its "when not to split" guidance - transposed from Microsoft 365 tenants to Jamf Pro instances and grounded only in what this deck already confirms (s04's resource-count figures, s15b's module and workspace structure, s-today's DevTest and Sandbox shape). Pick this if the goal is to explain the reasoning behind the split rather than the shape of one workspace. Accepting it means deleting the ws-opt-a, ws-opt-b and ws-opt-c wrappers from the #s-workspace section.
