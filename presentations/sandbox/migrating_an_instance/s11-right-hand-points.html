Slide 12 - tools and helpers, the right-hand points

Joseph asked for visual options on the right-hand side only, focused on four points: tidying with PRUNE, the jamfpy SDK, the regex pass, and rejecting -generate-config-out. That reduction ships with this PR and is the same in all four renders below - seven bullets down to four, each one a mono name over a single line. The three that came off (the per-candidate script and the structured map, the map pasted into a local with a for_each block, and AI-assisted validation) are already told by the pipeline diagram on the left or by slide 13, so nothing is lost. The left-hand diagram is untouched in every option.

What is open is how those four points are drawn. Each option is a real markup wrapper inside #s11 with its own CSS already in the deck, so the injected rule below only flips which wrapper is visible - and accepting one means deleting the other three wrappers and their rules as a single block.

Option A - four points as one list live now

What ships from this PR. The same dashed column the slide always had, but with four points instead of seven and each one split in two: the tool's name in the deck's monospace at heading size and in the accent colour, then one line of plain text under it saying what it did. The names carry the slide - PRUNE, jamfpy, regex and the flag - and the lines are there for anyone who wants them rather than for the speaker to read out. The rejected flag keeps the shape but turns its dash and its name to the danger colour, so the one thing the team said no to is legible from the back of the room without a card or a badge around it. Pick this if the right-hand side should stay quiet and let the pipeline diagram be the picture on the slide.

Option B - four cards, the tag doing the work

    
Each point becomes a navy card with a thick coloured edge down its left side, and the tool's name sits at the top of it as a large monospace tag - the card is really a label with a sentence attached. Because the cards butt up against each other the right-hand column reads as a stack of four equal things, which suits a slide that is a list of tools rather than a sequence. The fourth card is where this option earns its keep: its edge turns to the danger colour, its tag is struck through, and it carries the deck's existing rejected chip underneath, so the audience sees the decision before they read the reason. Pick this if you want the four names to land hard and the rejection to be unmissable.

Option C - a 2x2 grid with drawn glyphs

    
The four points become four tiles in a square block, and each one gets a glyph drawn in the deck's own diagram style - the same navy fill, hairline stroke and white line weight as the pipeline beside it. A bin for PRUNE, an angle-bracket mark for the SDK, a literal .* over a rule for the regex pass, and a code block with a danger-coloured line struck through it for the rejected flag. Nothing is imported and nothing is raster: they are four short inline SVGs using dg-box and dg-edge, so they inherit the tokens like everything else. The tiles give the right-hand side the same visual weight as the diagram, which balances a slide that currently leans left. Pick this if the slide should be looked at rather than read.

Option D - a used and rejected ledger

    
This one takes a position rather than listing four equal things. Three of the four points are what the team used, so they run down a vertical rail as ticks in the accent colour under a small USED heading, reading as a sequence the way the diagram next to them does. The fourth is the only thing on this slide that was tried and turned down, so it sits below a full-width rule under its own REJECTED heading with a cross instead of a tick, off the rail entirely. The layout makes the argument on its own: three tools in, one flag out, and the reason for the one that is out gets the bottom of the slide to itself. Pick this if the -generate-config-out decision is the part of this slide worth remembering.
