Landscape prior to the migration

We had no precedent to follow: nobody had migrated a live, in-use Jamf Pro instance to Terraform before, (let alone inside a bank).

Context

Our environment setup prior to the migration

Sandbox Staging Production

Requirements

  • No hardcoded secrets, anywhere, and all HCL must satisfy org policy linters.
  • Versioned releases, with change history findable when it is needed.
  • Post-migration, all create/update/delete operations happen through Terraform only.

Constraints

More detail

HCP Terraform runs plans and applies remotely on private runners inside the bank's network - state never touches a laptop. With the CLI restricted to development environments, every staging and production change flows through a VCS-triggered run.

This is a bank - the constraints are the story. No CLI outside dev means no local applies and no local state: everything flows through VCS-triggered runs.

What a Terraform workspace is

One set of Terraform code linked to one state file. How you carve a Jamf Pro instance into workspaces is a decision worth taking slowly, and there are more lenses on it than you would expect.

Plan Policy Apply
One Jamf Pro instance the target

Deciding how to carve an instance into workspaces is the part to slow down on. It is far cheaper to think it through than to re-cut it later. Four lenses come first:

Team structure Who owns what, and who needs to ship without waiting on somebody else's apply.
Deployment frequency How often each part actually changes, and whether those rates are anywhere near each other.
Scale Resource count, state size and plan time. Guidance puts the ceiling at roughly 500 resources per workspace.
What changes together Things that move at the same time belong together. Things that never move should not be dragged along.

Then refine against the rest: blast radius and risk appetite, dependencies between workspaces, environment strategy, approval and audit requirements, and how much orchestration you can realistically operate.

Define it plainly first - one set of Terraform code linked to one state file. Walk the diagram left to right: code goes in, the workspace is the boundary that holds the state, the variables and secrets, the permissions and the workflow, and a run comes out as a plan, then a policy check, then an apply against one Jamf Pro instance.

Then make the real point. How you carve an instance into workspaces is worth spending serious time on. Do not rush it. Re-cutting it later means moving state, which is a much harder day than getting the boundaries roughly right at the start.

Take the four lenses in order and give an example of each from our own split rather than reading them out. The last line is the honest caveat - there are more considerations than fit on a slide, and they refine the choice rather than drive it.

Migration outcomes we considered and rejected

We had a number of ideas that initially felt correct, but as we started to understand the implications they were dropped.

Rejected A single workspace for all resources

Blast radius and plan execution time. Guidance suggests roughly 500 resources per workspace; the estate holds 1,500+. At ~5,000, things break down.

Rejected Per-team Terraform modules scoped to each team's resources

Every change needs Mac team approval regardless of which repo it lives in. Splitting by team would just mean chasing that same approval across several repos instead of one - one repo keeps every approval flowing through a single place.

Rejected Managing everything with Terraform

Static group membership stays unmanaged to protect the support experience - troubleshooting should not require a pull request.

Expect pushback on "not everything in Terraform" - defend it: troubleshooting must not require a pull request.

Migration path options

Staging and production had already drifted apart by November 2025, so the order we worked in mattered.

01 Migrate Resource by resource in Staging first, then production Discounted because staging was not representative of production.
02 Production first, backported to staging a layer at a time Discounted because staging was not representative of production.
03 Migrate all of production resource by resource, then backport all of prod into staging in one big push Staging only started once production was complete. Chosen

The Terraform API client held read-only scopes, so importing built state with no surface to change the server. Write access came only when it was time to manage.

More detail

An import is read-only by nature: Terraform records the resource in state without writing to the server. Scoping the API client read-only removed the write surface entirely, so a mistake during import could not change Jamf Pro. Write scopes were added back once imports were stable with no recurring diff.

Three paths were genuinely on the table. Walk each diagram left to right - the left box is where a change lands first, the right box is where it goes next.

On path one the colour is the resource type - scripts, then dock items, then categories - and the same colour appears in both environments, so you can see all of one kind crossing before the next one starts.

Paths one and two both keep staging in the loop while production is still being built, and that is what killed them: staging was not representative, so validating against it proved nothing. Path three leaves staging until production is finished, which is the whole difference between it and path two.

Prod first is counterintuitive on purpose. Importing is read-then-manage - with a read-only API client there is no write surface, so it is safer than it sounds. Write scopes were only widened once imports were stable at zero diff.

Prerequisites

Instance prep

  • Tidy-up Big tidy-up: used PRUNE to export JSON of every unused resource, then removed them with a bespoke tool - jamf-resource-deleter - which backs each resource up to JSON before deleting it, with a restore path if anything was needed back.
  • Credentials Stored every instance's API client credentials in the secrets manager, verified each set was valid and complete, and tested the connection to Terraform Cloud end-to-end to confirm they were read correctly.
  • Version check Confirmed the Jamf Pro instance version met provider requirements.

Migration prep

  • Runner line of sight Confirm that your Terraform runtime environment has line of sight to each of your Jamf Pro instances.
  • Backout plan Agreed how to back out an import that went wrong before starting it.
  • Org-wide policies Ensure there are no org-wide policies blocking the actions you intend to take, specifically for Terraform or existing infra.

The tidy-up mattered - importing dead config would have codified years of cruft. PRUNE found the unused resources; jamf-resource-deleter removed them safely, with a JSON backup and restore path in case anything was needed back. Migration prep sits alongside it: runner line of sight, a backout plan and a check for org-wide policies, agreed before the first import.

Guardrails you don't own

At LBG, every Terraform run - across the bank's entire public cloud estate - passes through Sentinel policy checks before it can apply. One of those policies bans import blocks outright, because importing lets a workspace adopt resources someone else already manages.

  1. 1

    Ruled out. Import blocks are banned outright, and with no CLI access to production workspaces there's no terraform import fallback either.

  2. 2

    Excepted. A time-bound Sentinel exception, submitted - and chased - for every import window. Strings were pulled.

  3. 3

    Resolved. We made the case to the Sentinel team: sole actors on these workspaces, nobody else's resources to adopt. Standing exception granted.

More detail

Sentinel is HashiCorp's policy-as-code engine: policies evaluate every HCP Terraform run before it can apply. At LBG the same rails govern the bank's Azure and GCP estates, which is why the import ban is organisation-wide rather than per team.

Why the ban exists: Terraform runs the bank's whole public cloud - import blocks would let one workspace adopt someone else's resources. The policy is right; it just did not fit a sole-actor migration.

Each import window needed a fresh time-bound exception until the standing exception was granted.

Resource sequencing

One resource type at a time, end to end in production - not one instance at a time. The order came from the matrix: a group-built spreadsheet of every resource type and its dependencies.

The matrix is a spreadsheet the team built together. Risk scales with dependency fan-in: singletons carry none, scripts and categories and departments stand alone, smart groups and advanced searches and extension attributes sit on top of those, and profiles and policies sit on top of everything - so they close the migration.

Also considered migrating instance-by-instance - rejected in favour of one resource type at a time, end to end.

for_each exceptions

Just one exception

We kept policies in plain HCL.

They're too different from each other. One for_each map would have to carry every field any policy might need, and nobody could read it.

Once the map gets harder to read than plain HCL, the pattern isn't earning its keep any more.

Rebuilding staging

Production was code. Staging was years of drift, so we didn't import it.

  1. 1

    Wipe. We cleared staging out, keeping APNS and the cloud identity provider.

  2. 2

    Apply. We pointed production's configuration at the empty instance.

  3. 3

    Iterate. We fixed the errors, pass after pass, until the run came back clean.

Staging doesn't claim parity any more. It inherits it, from the same modules. TODO: confirm month (drives the timeline bar)

More detail

The wipe kept the things a rebuild cannot recreate without touching the fleet - the APNS connection and the cloud identity provider integration. Everything else on the instance was recreated by pointing production's modules at it and iterating until the run came back clean.

This is the highlight - slow down here.

Importing staging would have locked in years of drift. So we wiped it, kept APNS and the cloud identity provider, pointed production's configuration at it, and worked through the errors until the run came back clean. Parity is inherited now, not claimed.

Set up the next two slides. Rebuilding staging is what showed up the repo problem: a real staging environment is only useful if you can deploy there first, and back then a change there went straight to production too.

One codebase for every instance

Write it once, apply it everywhere. That was the objective.

DRY: one definition of a resource, deployed to every instance.

Jamf Pro does not allow it

resource "jamfpro_static_computer_group"
         "finance" {
  name    = "Finance laptops"
  site_id = 1

  assigned_computer_ids = [412, 887, 1043]
}
Shared The resource, its name, its site.
Unique to one instance The computer IDs. Computer 412 exists in production and nowhere else.

The resource is shared. Part of its configuration cannot be.

Start with the objective, because it is the one everybody in the room has had: one Terraform codebase, applied to every Jamf Pro instance, so a change is written once and deployed everywhere.

Then the block on the left, which is real provider schema. A static computer group takes computer IDs. Computer 412 is a machine in production, and it is nothing at all in staging, so that argument cannot be written once.

The point is not static groups. They were the exception we expected and planned for. The point is that the same resource type has to carry configuration belonging to one instance, and we kept finding more of it as we built.

Getting as close to DRY as we can

There is no technique that shares all of it. We use more than one of these.

Input variables

terraform.tfvars HCP Terraform variable sets

The resource stays shared. Only its values change per instance.

Values only

Local values

count = local.is_staging ? 0 : 1

One definition, switched on or off per instance with the count and for_each meta-arguments.

A switch in every resource

Data sources

data "jamfpro_computer_inventory" serial_number = each.value

The definition stays shared and the instance's own IDs are read at plan time.

One lookup per object

Child modules

module "iam" { source = "../../modules/iam_main" }

Shared configuration is written once in the modules. Each instance's root module holds only what is unique to it.

What we run

Configuration as data

instances/lbgstaging.yaml cfg = yamldecode(file(...))

The HCL is shared in full. Every difference sits in that instance's own data file, so adding an instance means adding a file rather than writing more configuration.

One file per instance

Terragrunt

include "root" { ... } inputs = { ... }

A unit pulls shared configuration in and supplies its own inputs. Terramate and Atmos solve the same problem their own way.

Outside Terraform

Not CLI workspaces. They share one backend, so they do not separate instances that need different credentials.

More detail

Our modules are iam_main, profiles_policies_main and root_main, called from a root module per instance under prod/lbgstaging and prod/lbgbusiness. Each root maps to one HCP Terraform workspace, and anything genuinely local to an instance sits in its own specific_to_here.tf. Payloads travel with the configuration that deploys them: privilege-set JSON, .mobileconfig profiles, scripts, Self Service icons and descriptions.

Six techniques, and the honest answer is that there is no right one. Read them as a menu, not a ranking.

We landed on child modules with a root module per instance, which is also what HashiCorp recommends where instances need different credentials and access controls. Shared code is written once; each instance's root holds only its own.

Worth naming the two we did not use. Keeping every instance difference in a data file means the HCL stops changing when you add an instance. Terragrunt was built for this problem, and Terramate and Atmos are the same idea productised.

Finish on the caution. CLI workspaces sound like the answer and are not, because they share a backend. Slide 4 already separated the two meanings of workspace.
